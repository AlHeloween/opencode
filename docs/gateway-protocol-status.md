# Протокол gateway в TUI

Строка `… (protocol)` в боковой панели показывает транспорт последнего отображаемого ответа: `h3`, `h2` или `http/1.1`. `auto` — настройка порядка попыток, не транспорт. Когда подтверждённого факта для этого ответа нет, строка показывает `unknown (protocol)`.

После успешной транспортной попытки `wrapFetch` публикует `gateway.protocol.selected` с `x-request-id`, поставщиком, моделью и фактическим протоколом. Событие проходит из серверного worker через `GlobalBus`/RPC в TUI. Панель хранит события по ID запроса и выбирает только запись для текущего пользовательского сообщения (`assistant.parentID`); у Novita заголовок содержит ID сессии. Совпадение поставщика и модели обязательно, а событие должно быть не старше создания текущего сообщения ассистента. Поэтому более ранний ответ или запрос другой модели не выдаёт чужой транспорт за текущий.

Событие может прийти до появления текста ответа: панель удерживает адресные факты до смены выбранного ответа. После перезапуска TUI прошедшие события не восстанавливаются, и строка честно показывает `unknown`. Провайдерский `customFetch`, который минует gateway, также не даёт gateway факта. Если плагин переопределяет `x-request-id`, панель не приписывает непроверенную запись текущему ответу.

Проверки: `test/provider/adaptive-client.test.ts` (локальный HTTP/1.1 и падение h3 с успешным h2), `test/tui/sidebar-protocol.test.ts` (адресация и `unknown`), `test/cli/tui/use-event.test.tsx` (доставка global event в активный workspace).

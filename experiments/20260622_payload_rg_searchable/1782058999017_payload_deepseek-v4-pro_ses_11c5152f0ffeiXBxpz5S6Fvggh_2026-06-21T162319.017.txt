## Real Blocking Factors vs Fake Blockers

A **real blocking factor** is a dependency, capability, or knowledge gap that prevents the plan from being implemented. "Complete previous step" is NOT a blocking factor — it is a task to finish. Examples:

| Real blocker (investigate) | Fake blocker (finish the task) |
|---------------------------|-------------------------------|
| "This library requires CUDA but only Vulkan is available" | "Need to finish the config module first" |
| "The API endpoint returns 401 — auth mechanism unknown" | "Step 3 must be done before step 4" |
| "Chromium CDP port 9222 is already bound by another process" | "Waiting for user to check something" |

**When you discover a real blocking factor during planning or implementation:**

1. **Check first, don't assume**. Verify exhaustively before declaring anything unavailable (see Blocking factor verification below).
2. **Create a smoke test plan**. Write a minimal, narrow test that isolates the blocking question and produces a yes/no answer. Place the smoke test plan in `plans/` alongside the main plan.
3. **If experiments are needed**: Launch a `general` agent with the smoke test plan as its task definition. ALL experiment artifacts go under `experiments/<ISO8601>_<short_descriptor>/`. The general agent receives clear boundaries:
   - What question the experiment must answer
   - What the success/failure signal is
   - Which folder to write outputs into
   - What NOT to modify outside that folder
4. **Feed the result back** into the master plan. If the experiment passes, continue. If it fails, update the plan with the finding and re-present Gate 4.

This keeps experiments bounded, traceable, and prevents random scripts scattered across the project root.
</blocking_factor_handling>

## Code Search

- For ALL codebase text search, prefer `rg` via bash directly. `rg` is faster than the `grep` tool and has no result-cap or line-length truncation.
- The `grep` tool wraps `rg --json` internally and limits output to 100 results with 2000-char line truncation — use it only for simple targeted searches where those limits are acceptable.
- `rg <pattern> <path>` — full text search with line numbers and highlighting
- `rg -l <pattern> <path>` — file names only
- `rg -c <pattern> <path>` — match counts per file
- `rg --files <path>` — list tracked files (respects .gitignore)
- `rg -u <pattern> <path>` — include gitignored files
- `rg -nu <pattern> .opencode/data/log` — search gitignored directories (logs, runtime data)
- When gitignored visibility matters: first `fd -u` to discover files, then `rg -u` to search them.
- For large output (500+ lines expected), wrap in cmd_runner to avoid blocking:
  `.\cmd_runner.exe start -- rg <pattern> <path>` then `.\cmd_runner.exe tail <run_id>`
- NEVER use: `--pre`, `--hostname-bin`, `--search-zip`, `-z` (they execute arbitrary commands).

- `fd -t f <pattern>` — files only (no directories)
- `fd -e ts <pattern>` — filter by extension
- NEVER use: `--exec`, `-x`, `--exec-batch`, `-X` (they execute arbitrary commands).

## ADID RAG — Local Code Retrieval

ADID RAG is a local-first semantic search engine for your codebase. It uses `fd`
for gitignore-aware file discovery, embeds source files into a vector index, and
answers natural-language queries with sub-second latency via MCP HTTP server.

### Quick Start

1. **Install dependencies** (one-time):
   ```bash
   pip install torch --index-url https://download.pytorch.org/whl/cu124
   pip install sentence-transformers
   ```

2. **Index the project** (`fd` respects `.gitignore`, SHA-256 incremental):
   ```bash
   adm --rag index <project_name> .
   ```

3. **Start the model daemon** (optional, for sub-second queries):
   ```bash
   adm-rag --mcp-http 127.0.0.1 7990
   ```
   Loads the BGE model once; all projects share it via `config_path` parameter.

### In This Project

- **Before any code search**, query the local index first:
  ```bash
  adm --query <index_name> "<your question>"
  ```
  Auto-forwards to MCP server if running (0.05s), otherwise loads model locally (~6-10s).

- **Index is incremental**: SHA-256 per file — unchanged files skipped.
  Embedder/chunker config change triggers full re-index.

- **File discovery**: `fd` (bundled in `tools/fd.exe`) walks the tree respecting `.gitignore`.
  Extensions from `include_globs` are passed as `--extension` filters.

- **Delegation**: Frozen `adm-rag.exe` (without torch) auto-delegates to system `adm`.
  `adm` forwards `--query`/`--rag`/`--mcp` to `tools/adm-rag.exe`.

### Commands Reference

| Command | Purpose |
|---|---|
| `adm-rag --init` | Check deps, advise if missing (never installs) |
| `adm-rag --rag-status` | Full environment health check |
| `adm --rag index <name> [roots]` | Create/update index |
| `adm --query <name> "<text>"` | Semantic search |
| `adm --rag status <name>` | Show index stats |
| `adm --rag docs <name> [limit]` | List indexed documents |
| `adm --rag delete <name>` | Remove index |
| `adm --mcp-http [host] [port]` | Start model daemon |

```

                  │                                            │

Project A → .adid_rag/data/A.sqlite3
Project B → .adid_rag/data/B.sqlite3
```

## KV Cache Continuity

The system prompt is **byte-stable** for the entire session — no timestamps, no mutable markers, no agent switches between turns. This ensures providers see identical SHA256(system prompt) → prefix KV cache hits → minimum recomputation → model preserves its reasoning chain across turns.

**Before modifying any code that touches the system prompt, user messages, or model message conversion, assess KV cache impact:**

- **System prompt** (`src/session/system.ts`, `src/session/prompt.ts` system construction): Must be byte-identical across all turns within a session. No dates, no counters, no `Date.now()`, no random values, no per-turn identifiers.
- **Agent resolution**: Same agent must be used for consecutive turns (including compaction). Switching agents changes `sys.skills(agent)` output → different system prompt → cache break.
- **Plugin hooks**: `experimental.chat.system.transform` in `llm.ts` receives `system[]` by reference. If a plugin modifies it, fingerprint must be computed AFTER the plugin runs, not before.
- **Date/time**: `environmentDate()` (`system.ts:147`) returns the date string — it must ONLY be injected into user messages, never the system prompt.
- **Message conversion**: `toModelMessagesEffect()` must not inject timestamps, random IDs, or mutable content into converted messages.

**Reporting rule:** If a proposed change has any probability of breaking KV cache continuity, the agent MUST:
1. Explicitly flag it with `[KV-CACHE RISK]` before implementing
2. Explain what would change (system prompt hash, message prefix, etc.)
3. Provide the alternative that preserves cache stability
4. If the change is unavoidable, document it clearly so downstream developers understand the cache invalidation

**Key files:**
| File | What | Cache sensitivity |
|------|------|-------------------|
| `src/session/system.ts` | System prompt construction | `environment()` must be static; date goes to user messages only |
| `src/session/prompt.ts` | System prompt assembly, fingerprint | System must be identical across paths; fingerprint stored post-plugin |
| `src/session/cache-control.ts` | Fingerprint computation | `partFingerprint` uses MD5(content) for text, not length |
| `src/session/llm.ts` | Plugin hook, provider request | Plugin can modify system by reference; fingerprint must be post-hook |
| `src/session/compaction.ts` | Compaction message creation | Same agent as original turn; `summary: true` on assistant |
| `src/session/message-v2.ts` | Message conversion | No mutable injection in `toModelMessagesEffect` |

## Style Guide

### General Principles

- Keep things in one function unless composable or reusable
- Avoid `try`/`catch` where possible
- Avoid using the `any` type
- Use Bun APIs when possible, like `Bun.file()`
- Rely on type inference when possible; avoid explicit type annotations or interfaces unless necessary for exports or clarity
- Prefer functional array methods (flatMap, filter, map) over for loops; use type guards on filter to maintain type inference downstream
- In `src/config`, follow the existing self-export pattern at the top of the file (for example `export * as ConfigAgent from "./agent"`) when adding a new config module.

Reduce total variable count by inlining when a value is only used once.

```ts
// Good
const journal = await Bun.file(path.join(dir, "journal.json")).json()

// Bad
const journalPath = path.join(dir, "journal.json")
const journal = await Bun.file(journalPath).json()
```

### Destructuring

Avoid unnecessary destructuring. Use dot notation to preserve context.

```ts
// Good
obj.a
obj.b

// Bad
const { a, b } = obj
```

### Variables

Prefer `const` over `let`. Use ternaries or early returns instead of reassignment.

```ts
// Good
const foo = condition ? 1 : 2

// Bad
let foo
if (condition) foo = 1
else foo = 2
```

### Control Flow

Avoid `else` statements. Prefer early returns.

```ts
// Good
function foo() {
  if (condition) return 1
  return 2
}

// Bad
function foo() {
  if (condition) return 1
  else return 2
}
```

### Schema Definitions (Drizzle)

Use snake_case for field names so column names don't need to be redefined as strings.

```ts
// Good
const table = sqliteTable("session", {
  id: text().primaryKey(),
  project_id: text().notNull(),
  created_at: integer().notNull(),
})

// Bad
const table = sqliteTable("session", {
  id: text("id").primaryKey(),
  projectID: text("project_id").notNull(),
  createdAt: integer("created_at").notNull(),
})
```

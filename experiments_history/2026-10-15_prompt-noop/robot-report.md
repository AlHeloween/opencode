## Вывод из фактов

На streaming-пути комбинация «user сохранён + быстрый 200 + нет loop0» кодового пути успеха НЕ ИМЕЕТ (единственный — опровергнутый noReply). Остаются два честных варианта: (а) 200 — это flush headers / лог на старте стрима, а эффект завис (loop не стартовал или завис до первого assistant); (б) эффект завершился быстро неизвестным путём (в `prompt()` до `createUserMessage` такого нет — user-то сохранён). Различает только измерение времени завершения ответа и счётчик вызовов провайдера.

## Гипотезы с falsifier

- H1 (зависший эффект, 200=headers): loop стартовал или завис до первого assistant (висящий fetch провайдера, отменённый токен, wedge). Falsifier: TestLLMServer с висящим провайдером должен дать ровно эту картину (user есть, assistant нет, стрим не завершён); мгновенный провайдер — полную. Добить измерением TTFB vs total в логе владельца.
- H2 (быстрое завершение): требует неизвестный ранний успех — в прочитанном коде отсутствует; держать как остаток, если H1 падёт.
- H3 (чужой путь): POSTы шли не на streaming-маршрут (проверить path в логе: `/prompt` vs `/prompt_async` vs иное). Falsifier: строки path из журнала.

## Короткий оракул (родителю, P2)

Матрица на TestLLMServer через фактический `InstanceRoutes`: (1) висящий провайдер → user persisted, assistant отсутствует, стрим открыт; (2) мгновенный → assistant + завершение; (3) `prompt_async` при падающем `svc.prompt` → 200-быстро + user + `"prompt_async failed"` в логе. Обязательно логировать TTFB и total ответа, счётчик вызовов провайдера, наличие assistant-строки. Контроль — прямой `SessionPrompt.prompt` в другом session (уже в плане ✓).

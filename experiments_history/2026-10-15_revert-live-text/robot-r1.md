## Установленная цепь (код, не предположения)

1. Revert ставит `session.revert` (сервер), TUI-стор получает через `patch → Event.Updated` (`session.ts:1016-1021`) → мёрж `Object.assign` (`sync.tsx:597-621`). Очистка revert при следующем промпте идёт тем же путём (`clearRevert`, `session.ts:1054-1056`). Пропущенной публикации нет.
2. Лента фильтруется `messagesList()` (`index.tsx:312-323`): без revert/partID — всё; иначе `revertedRun` скрывает хвост от якоря до следующего несинтетического user-сообщения. Новый ход с новым user-сообщением по построению видим.
3. Живые строки/текст идут `message.updated` → insert/reconcile (`sync.tsx:628-654`), `message.part.updated` → merge (`:710-741`), `message.part.delta` → буфер/батч (`:744-804`). Статус — `session.status` (`:623-625`), тем же SSE.
4. Навигация A→B→A размонтирует `Session()` и переподписывается: стор перечитывается bootstrap-загрузкой, все in-memory кэши (`compositeCache`, `displayItemCache`, `expandedMemory`) пересоздаются.
5. В кодовой базе уже задокументирован тот же силуэт симптома (09-27, `index.tsx:303-311`): рабочий агент + пустой транскрипт, лечилось рестартом/перевходом; тогда причиной был предикат `m.id >= revertID`, исправлен `revertedRun`. Нынешняя жалоба — либо рецидив другим путём, либо непокрытый остаток.

## Гипотезы (опровержимые)

- **H1 — разрыв wire/store нового хода.** Новые `message.updated`/`part.updated` не долетели (стор пуст по новым id), статус долетел (индикатор жив). Навигация лечит bootstrap-перечитом. Falsifier: `arrived`-множество (`sync.tsx:629-636`, пишется ДО reconcile) сразу после repro не содержит новых id. Отклонено заранее: версия «clearRevert не публикуется» — кодом (`session.ts:1021` публикует; `sync.tsx:605-611` мёржит).
- **H2 — фильтр держит новый ход.** Новые строки в сторе есть, но `messagesList()` их режет: несброшенный `session.revert` в сторе + якорь, покрывающий новые id (напр., ход без нового user-сообщения — повтор/регенерация на старых id, либо синтетический маркер нового user). Falsifier: новые id есть в `sync.data.message`, но `listed` в divergence-отчёте их не содержит (`index.tsx:330-340`). Прогноз: повторный промпт новым текстом симптом снимет, повтор — нет.
- **H3 — стор полон, рендер не сошёлся.** `listed` содержит новые id (divergence-лог), пикселей нет: кэши идентичности (`displayItemCache`, `index.tsx:403-426`; `compositeCache`, `:265-285`) или `<For>`-reconcile. Falsifier: listed-полнота при пустом кадре. Навигация лечит пересозданием кэшей.

## Самый короткий различающий оракул (без навигации)

1. Revert → новый промпт → дождаться busy + 15–30 с тишины.
2. Не уходя из сессии, снять три среза: (а) wire — шли ли `message.updated`/`part.updated` нового хода (лог SSE/сервера); (б) store — `arrived`-id и `sync.data.message/part` по новым id; (в) render — `listed` из divergence-репорта + кадр.
3. Решение: нет в (а) → H1; есть в (а,б), нет в listed → H2; есть в listed, нет на кадре → H3.
4. Контроль без навигации: тот же промпт в свежей сессии без Revert (текст идёт → специфично Revert-пути, а не общему стримингу).

## Пробелы плана R1–R3 (план не редактировался)

- R2 не называет инструменты тройного среза (`arrived`, divergence-`listed`, SSE/wire) и контроль без навигации — есть в задаче, нет в боксе.
- R3 «соседняя сессия» не конкретизирует, что она проверяет (изоляция стора vs фильтр); добавить предсказание до исполнения.

## Что воспроизвести

Один живой прогон Revert→промпт с включённым divergence-логом и захватом SSE; затем чтение `arrived`/`listed`/кадра до любой навигации. Этого достаточно, чтобы убить две гипотезы из трёх.

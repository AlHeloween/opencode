## Two-Phase Explorer Grounding (reinforcement)

The primary model orchestrates — it does NOT perform first local work on non-trivial tasks.

1. **Phase 1 — Broad scan**: Launch an `explore` task agent for: web searches, task scope discovery, relevant file identification, current state, logs, tests, and conversation context. Give it precise search targets. The explorer is fast but has no reasoning — it needs exact instructions on what to find and where.
2. **Analyze Phase 1**: Read and cross-check the explorer's evidence against concrete files, logs, tests, or tool output. Identify gaps. Correct weak assumptions.
3. **Phase 2 — Gap fill**: Launch a second `explore` agent for the specific gaps found. Use `universalsearch` or `webfetch` for external, versioned, API, package, pricing, or current-event claims. Update the plan with findings.
4. **Implementation gate**: Only after both phases complete and the plan is grounded — begin writing code.

**Explorer goal precision**: Because the explorer has no reasoning, every search must be framed as a specific question with bounded scope. Example:
  CORRECT: "Find all functions in src/agent/ that call `submit_turn`. Return file paths, line numbers, and function signatures."
  WRONG:   "Search the agent codebase for relevant things."

**Delegation exceptions** (primary may act directly):
- `cmd_runner` session management (status, tail, send, stop, log interpretation) — no explorer needed.
- User explicitly forbids delegation.
*Even in exceptions*, read current object state before acting.

<blocking_factor_handling>
## Real Blocking Factors vs Fake Blockers

A **real blocking factor** is a dependency, capability, or knowledge gap that prevents the plan from being implemented. "Complete previous step" is NOT a blocking factor — it is a task to finish. Examples:

| Real blocker (investigate) | Fake blocker (finish the task) |
|---------------------------|-------------------------------|
| "This library requires CUDA but only Vulkan is available" | "Need to finish the config module first" |
| "The API endpoint returns 401 — auth mechanism unknown" | "Step 3 must be done before step 4" |
| "Chromium CDP port 9222 is already bound by another process" | "Waiting for user to check something" |

**When you discover a real blocking factor during planning or implementation:**

1. **Check first, don't assume**. Verify exhaustively before declaring anything unavailable (see Blocking factor verification below).
2. **Create a smoke test plan**. Write a minimal, narrow test that isolates the blocking question and produces a yes/no answer. Place the smoke test plan in `plans/` alongside the main plan.
3. **If experiments are needed**: Launch a `general` agent with the smoke test plan as its task definition. ALL experiment artifacts go under `experiments/<ISO8601>_<short_descriptor>/`. The general agent receives clear boundaries:
   - What question the experiment must answer
   - What the success/failure signal is
   - Which folder to write outputs into
   - What NOT to modify outside that folder
4. **Feed the result back** into the master plan. If the experiment passes, continue. If it fails, update the plan with the finding and re-present Gate 4.

This keeps experiments bounded, traceable, and prevents random scripts scattered across the project root.
</blocking_factor_handling>

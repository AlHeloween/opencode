## Mutation class

`apply_patch` is **MODIFY / PERSISTENT_WRITE / ELEVATED** (multi-file atomic; @ACTION_CLASS).
Same grounding as edit/write: @G7, @WRITE_SCOPE, @SMOKE_BEFORE; premises ⊆ G when a
@CLAIM_LEDGER is active. After apply: run declared oracles (@G8 / @VERIFY_OUTCOME) before Done.
Prefer when coordinated multi-file changes must succeed or fail together.

Apply multiple file changes in a single atomic operation using a structured patch format.

## Patch Format

Each patch uses this envelope:
```
*** Begin Patch
<operation description or comment>
*** Operation: <Add File|Update File|Delete File>
*** Path: <file path>
*** Move to: <new path>  (optional, for renaming during Update)
*** Content
<file content or diff>
*** End Patch
```

## Operations

- **Add File**: `*** Content` section contains the full new file content.
- **Delete File**: No Content section needed.
- **Update File**: Uses `@@` hunk headers with context lines (same format as unified diff). The `*** Move to:` header is optional for renaming.

## Post-Edit Processing

- **LSP diagnostics** run on all modified files. Errors are reported in the output.
- **File formatting** respects the project's configured formatter.
- **UTF-8 BOM** is preserved/detected.
- **Permission integration** — shows diffs before applying for user approval.

## Atomic Application

All file changes in a single patch are applied atomically. If any individual change fails, none are applied.

## When to Use

- Making coordinated changes across multiple files
- Renaming files during edits (Use `*** Move to:`)
- Operations where partial application would leave the project in a broken state
- Applying a unified-diff-style proposal (e.g. from `aicall`) after human/agent review — `aicall` output alone is never Done

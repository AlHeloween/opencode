Recover the content of an earlier tool result by its id, with line numbers so you can narrow it.

Why this exists: a completed tool result heavier than 8 000 characters is replaced on the wire by a
one-line placeholder once its turn is no longer the one being continued:

  [grep id=prt_0b8da48fb001xD6AvY4MQp2Mo0 — result delivered earlier (10.0 KB, <pattern>) —
   first 6 of 412 line(s), to judge without paying a round trip:]
  1: <first line>
  …
  … recall(id=prt_0b8da48fb001xD6AvY4MQp2Mo0, range="<line>-") for the rest]

Only the copy sent to the provider was dropped — the bytes are still stored in the session. `recall`
reads them back by that id.

Every answer opens with the SAME label the placeholder printed — `<tool>: <title>`, for example
`recall: grep: log\.(debug|info) — id=prt_0b8da48fb001…`. One handle in both places, so a recalled
result cannot be confused with another one recalled in the same turn.

How to use it:
1. Call it with just the id to see the whole result as `N: text` rows — every line carries its
   ABSOLUTE line number, so the next call can address them.
2. Then narrow: `range` picks a window, `pattern` filters inside it. Only what you ask for is sent.
3. Add `keep: true` to LEAVE exactly that selection on the result. From then on the replay carries
   these lines instead of the placeholder, so the result stops costing what it used to — this is what
   turns the call into an optimisation rather than a tax. Ask for more lines later with another recall.

The placeholder itself already shows the first lines of what was dropped, numbered, so you can judge
whether it is worth fetching BEFORE you pay for fetching it.

Parameters:
- `id` (required) — the `id=` value printed in the placeholder.
- `range` — 1-based inclusive: `"120-180"`, `"120-"`, `"-180"`, `"42"`, or `0` for everything.
  Each answer prints the next range to continue with, so a result larger than the cap is walked.
- `pattern` — a regular expression; only matching lines inside the range come back, keeping their
  absolute numbers.
- `maxChars` — body cap, defaulting to the same 32 000 ceiling the replay path applies.
- `reason` (required) — why you are reading this, and why the kept slice is enough. It is stored WITH
  the selection, so a narrowed result can be audited later instead of being a silent edit.

Errors ARE recallable: an errored result is exactly what tells you to discard or repair a step, so
refusing it would hide the failure behind a count. Only a result that never finished is refused.

And errors are the case where `keep` matters MOST, because an errored result has no size gate at all:
it replays in FULL on every later turn until something shrinks it. Read the part that matters, then
`keep` it — that is what stops a failure from spamming the context for the rest of the session. Put
the mistake itself in `reason` ("multiedit: stale anchor; re-read the region first") so the same error
is not repeated.

Not a substitute for `sessionread`, which truncates every tool output to 500 characters. And when
the placeholder's advice cannot be followed — a `task` result cannot be reproduced at all, and
re-running `bash` re-applies its side effects — `recall` is the only way back.

Recalled content is attached to the current request only and is not remembered as part of history,
so asking twice costs twice and leaves nothing behind.

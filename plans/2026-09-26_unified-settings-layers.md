# Unified settings layers — global → worktree → session (owner spec, 2026-09-26)

**Статус:** ACTIVE. Спецификация владельца ниже — дословно; сверка с кодом — по состоянию на 2026-09-26.
Основание: `plans/to_be_confirmed/2026-09-19_fill-every-settings-layer.md` (правило «fill, do not search» частично реализовано: worktree/session fill; global fill — нет).

## 0. Owner spec (verbatim)

1. «У нас есть глобальные настройки, если нет то создаем и прописываем любую free model из opencode zen чтобы было зрение и большое окно.»
2. «У нас есть worktree, если нету - копируем из global, выбор модели для worktree берется из global и из /agents мы редактируем global - вкладка открывается автоматически, после создания проекта создаются настройки worktree и соответственно настройки session из этого worktree.»
3. «У нас есть session - при создании новой сессии настройки берутся из worktree или из global если нету worktree, если есть то /agents открывае вкладку worktree... и заполняется session. Выбор из этого режима берется из worktree.»
4. «Все настройки прописаны, для существующей сессии все настройки и редактирование session. /agents открывает session.»
5. «Все параметры для работы берутся только из session и она должна обязательно быть.»

## 2. Задачи

- **T1 — global fill (уточнения владельца 2026-09-26: «не просто free, а модель со зрением и максимально большим окном контента»; «Big-Pickle это fail protection и не рекомендуется»).** Если global не содержит моделей агентов: seed всех агентов моделью zen с приоритетом: (1) FREE + `capabilities.input.image === true` (зрение) + максимальный `limit.context`, provider = `opencode`; **big-pickle исключён из основного отбора** — он допускается только как fail-protection, когда иной free+vision модели нет. Если build-модель уже объявлена — сохранить её. Writer — серверный путь `writeGlobalAgentField` (`local.tsx:599`), один PATCH на всех. Оракул: unit на chooser (free+vision+maxctx поверх шума; big-pickle не побеждает при наличии альтернативы) + temp-конфиг без агентов → после fill у каждого агента есть model; read-back файла.
- **T2 — авто-вкладка /agents.** Дефолт вкладки — по фазе, не по kv: нет worktree-слоя → `global`; worktree есть, session этой сессии не полна → `worktree`; всё заполнено → `session`. Kv остаётся для ручного переключения (не как источник дефолта). Поверхности: `dialog-agent.tsx:46-48`, `dialog-model.tsx:45-47`.
- **T3 — worktree-пик в фазе новой сессии доходит до session.** Правка `shouldUpdateSessionModelOnPick` (или вызов fill после пика) + замена ассерта `agent-selection.test.ts:33`.
- **T4 — session обязателен для рантайма.** Проверить серверные fallback-цепочки (`prompt.ts:1289` и соседние): параметры работы берутся только из session; отсутствие session-записи — bug-warn, не parent-walk.
- **T5 — smoke/приёмка.** S1: worktree без настроек ← global; S2: пустой global ← free-zen; S3: session ← worktree; S4: copy-not-link (изменение worktree не течёт в session); S5: вкладки открываются по фазам (global → worktree → session); S6: рантайм-запрос уходит на модель из session. Каждый — read-back файла, не typecheck.

## 5. Addendum — owner, 2026-09-26 (verbatim уточнения)

1. **Фаза без сессии.** «Смотри если сессия не создана то измения меняют параметры активного агента, кстати не меняют выбор активного агента. Ну а если пошло создание ... ну дальше по процедуре.» → без открытой сессии `/agents`-правки пишут параметры в слой **worktree** для активного агента и **не переключают** активного агента; после создания сессии — процедура: session ← worktree, вкладка session (T2/T3 уже это описывают; закрепить тестом).
2. **Протокол и routing — часть настроек.** «не забывай про выбор протокола и роутинг для openrouter» → transport (h3/h2/http1.1) и openrouter routing живут в тех же слоях (global/worktree/session) и выбираются в `/agents`, как модель.
3. **Индикация протокола в TUI.** «сейчас в tui: h2 (protocol) если auto-> auto(выбранный протокол) если не auto протокол» → режим `auto` отображается как `auto(<разрешённый протокол>)`, не-auto — как сам протокол.
4. **Протокол фиксируется при выборе настроек, а не при запросе.** «протокол должен определяться при выборе настроек, а не при запросе» → выбор/резолв протокола записывается в слой при настройке; запрос читает готовое значение (тот же принцип fill/read, что и у модели).
5. **Observability — на берегу.** «Политика такая observability на берегу - мы знаем с какими настройками лезем» → конфигурация известна ДО запроса: слои видны в `/agents` и в статусе; рантайм читает готовую session-запись и ничего не решает «на лету». Незаполненный слой — дефект fill: `bug:`-warn фиксирует его, но не является рабочей веткой и не способом узнавать настройки.

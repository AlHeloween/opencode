## Rules for the gate and the watcher

- **A process you did not start is never killed — you name it and route it to its owner.**
  Owner, 2026-10-21 (review 2): on 2026-10-21 at 14:48:48 and 14:49:45 this agent ran `taskkill` on pids
  18160, 16976 and 32496 — Claude's own `run_in_background` watchers. That was a protocol violation AND a
  harm: the EXIT of a watcher is the delegator's wake-up channel, and a replacement this agent starts
  (under cmd_runner) cannot wake Claude at all — the delegator had to build a separate waiter. The right
  move is to REPORT the stale watchers («pre-fix watchers 18160/16976/32496 are running; restart them»)
  and let their owner restart them. A process whose start you cannot account for is not yours to stop.
- **The gate and the watcher share ONE definition of a watcher** (`watch3_procs.is_watcher`): a live
  `python` process running `watch3.py` whose command line names the session. A launch wrapper
  (`bash -c 'python watch3.py …'`, cmd_runner) carries the same command line in its OWN and is not a
  watcher — measured 2026-10-21: one watcher appears as 3 nested `bash` launchers + 1 `python`.
- **The live robot set is ONE registry** (`session_tasks.json`): read by the gate and by the seed, written
  by `robot_registry.record_task` (the dispatcher and the note-sender are its two writers). The history
  (`sessions.json`) is not the live set.

## Residuals

- The gate fails OPEN when the host is unreachable (documented, with a log row): a dead host cannot be proven busy, and blocking every turn would make the delegator unusable.
- The ledger is append-only and never expires: a message id stays verified even if the same session later produces another final — the new final is a different id, so it is unverified until checked (that is the point).
- The gate reads the watcher from the PROCESS LIST: a watch3 started with a different argument order (`ses_…=name`) still names the session in its command line, so both orders are covered; a watcher started with NO session argument covers nothing and is correctly not counted.
- The live check exercised the ALLOW path only: a live BLOCK needs a real busy robot with no watcher, which is the owner's next dispatch to produce.
- The three watchers this agent started on 2026-10-21 (pids 5784 t118, 11820 t123, 28872 t124) still hold the one-watcher slot for those sessions, and they run under cmd_runner — their exit re-invokes THIS agent, not the delegator. So they are coverage for the gate but NOT the delegator's wake-up channel, and with the T9 refusal in force a delegator-started watcher for those sessions is REFUSED while they live (the message names the pid). They are this agent's processes, so their owner may stop them; the delegator then starts its own `run_in_background` watcher, which is the channel that can wake it.
- The live registry is append-only and never pruned: every dispatch adds an entry, and the gate issues one GET per entry on every Stop event (measured: 9 entries → ~2 s, against the hook's 25 s budget). The cost grows linearly with the number of dispatches; nothing prunes the verified-and-idle tail.
- The watcher predicate keys on the process IMAGE beginning with `python` (measured: the delegator launches `python.exe`). A watcher started by another interpreter would not be counted as a watcher, and the gate would report «no watcher» for it.

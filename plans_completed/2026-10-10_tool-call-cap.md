# Кап на число tool-call'ов в одном assistant-ходе

## Что измерено (2026-10-10, Exact — dbread по `opencode.db`)

Сообщение `msg_125072648001canagLg4o3lNUt`, модель `xiaomi/mimo-v2.6-flash` через openrouter:

| Метрика | Значение | Инструмент |
|---|---|---|
| `step-start` / `step-finish` | **1 / 0** | dbread |
| tool-call'ов в сообщении | **2444** | dbread |
| уникальных `(tool, input)` | **397** | dbread |
| **точных дубликатов** | **2047 (83.8 %)** | dbread |
| аргументов суммарно | ≈ 109 KB | dbread |
| скорость | 32 вызова за первые 5 с | dbread |
| исход всех вызовов | `Tool execution aborted` × 2444 | dbread |

Топ вызовов: 9 уникальных `(tool, input)`, повторённых по ~228 раз каждый.

## Корневая причина: существующий guard не ловит цикл

`processor.ts:958-979` — `doom_loop` срабатывает, только когда **последние 3 вызова подряд** полностью совпадают
(`last.every((c) => c.toolName === … && Bun.deepEquals(c.input, …))`).

Шторм чередовал **9 разных** вызовов по кругу (`callers → node → search → callers …`), поэтому условие
`last.every(...)` **никогда не выполнялось**, и guard молчал, пока ход не прервали вручную.

## Почему кап 64, а не только кап на токены

- Кап «64k output-токенов» (≈256 KB) по этому же замеру сработал бы на **≈344-й секунде**.
- Фактический ход был срезан абортом на **156-й секунде**.
- Кап на **число вызовов** при 32 вызовах/5 с срабатывает на **65-м вызове ≈ 10-я секунда**.

## Изменение

`packages/opencode/src/session/processor.ts`:

1. `ctx.toolCallCount: number` — рядом с `recentToolCalls` (`processor.ts:581`), счётчик **на assistant-сообщение**
   (`ctx` пересоздаётся на каждое сообщение, `processor.ts:581` — точка истины).
2. `MAX_TOOL_CALLS_PER_MESSAGE = 64` рядом с `DOOM_LOOP_THRESHOLD = 3` (`processor.ts:69`).
3. В `case "tool-call"` (`processor.ts:917`) — инкремент; при превышении part переводится в `running`
   (как сейчас), затем `failToolCall(value.toolCallId, …)` с сообщением, называющим кап и инструмент, и `return`.

Отказ **виден в part** (`status: "error"`), а не проглатывается: правило проекта — «absence of an oracle reads
as FALSE». Модель на следующем шаге видит ошибку и может завершить ход; легитимный ход со 100 правками
деградирует до 64 + 36 отказов и продолжается следующим шагом, а не падает.

`doom_loop` **не трогаем** — это другой сигнал (3 одинаковых подряд = осознанный повтор), он объявлен в
`config/permission.ts:60`, `agent/agent.ts:100`, `dialog-navigation.tsx:95,162`,
`routes/session/permission.tsx:487`, `tips-view.tsx:139`.

## Риски

- **R1 (критический)**: кап режет легитимный ход с >64 вызовами. Митигация — отказ назван, ход продолжается
  следующим шагом; порог 64 выбран как «заведомо больше нормального шага, заведомо меньше шторма».
- **R2**: `ctx` пересоздаётся на сообщение — при `providerExecuted` вызовах счётчик может не увидеть часть
  вызовов. Митигация: считаем то, что проходит через `case "tool-call"`; замер это подтверждает.
